# SQL DDL import feasibility for 2.7.2

[#42](https://github.com/rheiger/markWriter/issues/42) stays open for PostgreSQL and SQLite3. The release candidate adds no SQL import command or parser dependency.

The disposable probe used synthetic schemas with quoted names, Unicode, composite primary and unique keys, and a composite foreign key. On the 2.7.1 DBML renderer, PostgreSQL output from `@dbml/core@11.0.1` failed on its optional reference markers. Removing the references exposed an unquoted composite index column with a space. Appending an INSERT produced byte-identical DBML. Passing the synthetic SQLite schema to the same importer with the `sqlite` format argument produced empty output.

A second probe used `pgsql-ast-parser@12.0.2` and `sqlite-parser@1.0.1`. Separate adapters converted the two sample ASTs into structured models and emitted fresh, quoted DBML. The actual renderer's DBML-to-DOT stage accepted both; assertions checked the tuples and foreign-key direction. The adapters rejected the sample INSERT, default and foreign-key action. No database or hosted renderer was used.

The PostgreSQL prototype still fails to derive implicit NOT NULL from a primary key. SQLite allows nullable composite primary keys in ordinary tables, needs case-insensitive identifier resolution, and requires separate handling for rowid aliases, WITHOUT ROWID and STRICT. The tested SQLite parser rejected STRICT and reported identical AST action metadata for ON UPDATE and ON DELETE CASCADE. The next gate is a strict dialect-specific adapter with representative scrubbed inputs, semantic comparison, explicit rejection of unsupported constructs and measured parser bounds. Then qualify cancellation and the native import-to-Undo workflow.
