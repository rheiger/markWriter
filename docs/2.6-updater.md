# Update discovery and installation qualification

Issue [#59](https://github.com/rheiger/markWriter/issues/59) asks for a manual check and app-controlled installation. The bounded release-discovery slice and the installation gate are separate. Discovery does not authenticate an update or install one; #59 remains partial until an authentic installed update passes.

`src-tauri/src/update_policy.rs` checks the fixed GitHub releases API for this repository, not `/latest` (which is intentionally an older release). It examines at most the first 100 results, rejects a full page as potentially incomplete, ignores drafts and prereleases, and compares canonical stable numeric `major.minor.patch` tags. It rejects unknown current-version formats instead of guessing. The request uses TLS, no redirects, bounded response size and timeouts. Network failures and other errors are distinct; raw remote error messages are not shown. The result is a release-discovery signal, not a signed manifest, installation authorization, promise that every package exists, or proof of authenticity beyond the normal HTTPS connection. API rate limits, a missing network, prerelease app versions and malformed/large/incomplete responses can prevent a definitive result. No automatic checking occurs.

`UpdateDialog` displays the result and explicitly states that installation is unavailable when a newer release is found. It never starts a download or links to a browser as an installation substitute. The main application must wire this dialog to the Rust command with a stable callback and preserve existing modal behavior. An integration test must cover real menu invocation and errors. As of this checkpoint, the leaf UI tests and isolated manifest test pass; the Rust leaf requires integration/compilation and actual desktop acceptance before claiming the feature.

The independent `tools/update-prototype.mjs` uses an ephemeral loopback-only test server in its tests. It bounds response/time, rejects redirects and non-loopback endpoints, checks stable numeric ordering and required artifact fields, and labels every newer candidate **unverified**. It does not verify signatures, secure a production connection, enforce download limits or install anything, and must never be wired into the app. Tests also do not establish replay protection or a secure update feed.

Tauri's [updater documentation](https://v2.tauri.app/plugin/updater/) requires artifact signatures and a public key in the installed app. It describes macOS app tarballs, Windows NSIS/MSI, and Linux AppImage artifacts; this project's DEB is not an updater-supported artifact established by that documentation. The released 2.5.1 application contains no updater trust key, so users need a manual bootstrap before future app-driven upgrades. Release metadata discovery is not the same trust model as verifying update artifacts. The run generated a **test-only ephemeral updater key** and signed a synthetic text fixture using the locked Tauri CLI; output and key material were not printed. The signature's presence is only a signer smoke test: verification, malicious/wrong/missing signatures, installation, rollback and key recovery were not tested. Public test fixtures/signatures are isolated in the run's `evidence/updater/`; the private test key is mode 600 under owned `tmp/updater-private/`, excluded from artifact/source uploads and must never be used as production credentials.

Before an installer is exposed, choose and review the production key custody, backup, rotation and recovery process; explicit trusted HTTPS endpoint and channel policy; stable/prerelease ordering and replay/downgrade handling; artifact identity, redirects and size limits; and per-platform package support. Qualify exact locked plugin and toolchain compatibility, independent update-signature verification and OS signing where applicable. In a disposable installation using a distinct test key/feed, verify authentic A→B bytes, wrong/missing signatures, interrupted downloads, offline/TLS errors, downgrade and channel cases. Preserve user documents and recovery through explicit installation/restart consent; ensure dirty-document changes are not lost. Linux DEB requires a separately qualified package-manager path or an explicit unsupported disposition. No real feed, production key, OS-signing operation or installed upgrade is enabled by this work.
